# Migration from the prototype

> **A historical record - the migration is done.** The firmware it planned is
> the one in `firmware/src/`. The target directories named below (`printers/`,
> `reader/`, ...) were not adopted: the sources stayed flat in `firmware/src/`,
> one `backend_*` file per brand. [CODEMAP.md](../CODEMAP.md) is the map of what
> exists. This file is kept for the prototype facts it records.

TigerSpool is not written from scratch. A working prototype exists, was tested
against four real printers, and is the source of every protocol fact in this
repository. This document is the plan for turning it into the firmware described
in [ARCHITECTURE.md](ARCHITECTURE.md).

**Prototype:** `RP3D-S/k2-tigertag-bridge` (private) — ~9,500 lines of C++ in
total, of which **~3,200 are the project's own code** and the rest is a vendored
NFC library carried three times over.

---

## What is actually there

The prototype is a multi-project PlatformIO tree. Only one of the four projects
is the real firmware.

| Path | Lines | What it is | Verdict |
|---|---|---|---|
| `tools/cfs_ui/src/` + `include/` | ~3,170 | The complete application. Bench-tested. | **The firmware.** Migrate. |
| `tools/wifi_portal/` | 309 | Standalone captive portal | **Delete** — superseded, see below |
| `tools/pn532_screen/` | 265 + a DB generator | Reader diagnostic with display | Keep the **generator**, drop the app |
| `tools/pn532_check/` | 173 | Serial-only reader diagnostic | Keep as a bring-up tool |
| `src/` + `include/` at the root | ~630 | First draft, written **before any hardware existed** | **Delete.** See below. |
| `lib/PN532Seeed/` × 3 | ~1,190 each | Vendored NFC driver, three diverged copies | **Deduplicate to one** |

### The root `src/` must not be migrated

It targets `Adafruit_PN532` over I²C, uses LVGL, and wires the reader to
**GPIO6/7**. All three are wrong on this hardware — the reader is HSU on
GPIO43/44, the UI is LovyanGFX, and GPIO6/7 is an I²C bus with pull-ups that
silently corrupts every read ([WIRING.md](WIRING.md)).

The prototype's own README carries this pin table, which is why the wrong pinout
has propagated into later notes. **Deleting this tree is part of the migration**,
not an optional cleanup — as long as it exists, someone will read it.

### The standalone Wi-Fi portal is already obsolete

The prototype's `CLAUDE.md` and its own README describe flashing
`tools/wifi_portal`, configuring, then flashing the real firmware. **That is no
longer true of the code.** The main application already contains a full captive
portal that starts automatically when Wi-Fi fails: `webcfg::beginAP()` brings up
an access point with a DNS wildcard, a network scan and captive-detection
endpoints, and the state machine enters it on a 30-second connect timeout.

`tools/wifi_portal` is a leftover from before that was merged. It is dead weight
that makes the product look worse than it is, and it goes.

## The vendored PN532 library

Three copies exist, and **they have already diverged** — which is the argument for
deduplicating, not a hypothetical one:

| Difference | `cfs_ui` | `pn532_screen` | `pn532_check` |
|---|---|---|---|
| Inter-command delay | `10 ms` | `2 ms` | `2 ms` |
| `mifareultralight_ReadPage16` | present, with a response-length check | present, no length check | **absent** |

Only the `cfs_ui` copy validates the response length before accepting data — and
that check is what stops a truncated HSU response from being read as 16 bytes of
zeros. The two other copies would accept it. That is not a stylistic difference;
it is a correctness bug in two of three copies.

**One copy, in `firmware/lib/PN532/`, with the patches documented in its own
README.** The patches carry over as a set:

1. **A wake-up preamble before every command.** These modules power down between
   commands; without this only the first command after boot answers.
2. **Reduced inter-command delays** — 100 ms down to ~10 ms. Fast enough to read
   a tag held briefly, with margin for a marginal link.
3. **`mifareultralight_ReadPage16`** — reads the 16 bytes the `READ` command
   returns in one transaction instead of four, **with the length check**.

Each patch needs a comment saying what breaks without it. A future maintainer
updating the upstream library will otherwise delete them and reintroduce three
bugs that took days to find.

## Renames

The prototype is named for a Creality K2. None of those names survive.

| Prototype | TigerSpool | Migration cost |
|---|---|---|
| NVS namespace `k2cfg` | `tigerspool` | One-time migration on first boot, or accept re-provisioning |
| mDNS `tigertag.local` | `tigerspool-xxxx.local` | None — `tigertag.local` collides with other ecosystem devices |
| AP `K2-TigerTag-XXXX` / `TigerTag-Setup` | `TigerSpool-Setup-XXXX` | None |
| PlatformIO env `cfs_ui` | `tigerspool` | None |
| `K2Backend`, `beK2`, `k2::` | `CrealityBackend` | Mechanical |
| `p0t`/`p0n`/`p0h`/`p0s`/`p0c` NVS keys | keep the shape | These are fine; only the namespace moves |

**Decide whether to migrate `k2cfg` → `tigerspool` on first boot.** The prototype
already has precedent for this — it migrates a single `k2ip` key from an older
format and persists the result. Only bench devices carry `k2cfg` today, so the
cheaper answer of re-provisioning them is defensible; it just has to be a
decision, not an accident.

## Order of work

Each phase leaves a firmware that builds and runs. No phase is a rewrite.

**1 · Promote and rename.** Move `tools/cfs_ui/` to `firmware/`, delete the root
draft and `wifi_portal`, deduplicate the PN532 library, rename the identifiers,
translate every comment to English. *No behaviour changes.* This is the phase that
makes the repository honest, and it is one commit's worth of thinking spread over
many files — do it first and do it completely.

**2 · Partitions and OTA.** Set the partition table before anyone owns a device,
because changing it later costs a USB reflash for every user. Then implement
update, verification and rollback. [OTA.md](OTA.md).

**3 · Split `main.cpp`.** Extract `ui/`, `app/`, `net/`, `platform/`. Layout out
of drawing code.

**4 · Account layer.** TLS verification on, encrypted NVS, non-blocking sync, and
the pairing QR **on the device screen** rather than only in the web page.
[ACCOUNT-PAIRING.md](ACCOUNT-PAIRING.md).

**5 · Web UI and i18n.** Static page from LittleFS, JSON API, 9 locales,
generated fonts, CI checks.

**6 · Elegoo and Anycubic.** A **port, not a reverse-engineering exercise** — both
protocols are documented and working in
[Tiger Studio](https://github.com/TigerTag-Project/TigerTag-Studio-Manager)
(`renderer/printers/{elegoo,anycubic}/PROTOCOL.md`), captured live from the
vendors' slicers. What has to be proven on hardware is that the ESP32's TLS stack
negotiates Anycubic's broker, which insists on TLS 1.2 and requests an optional
client certificate. [PRINTER-COMPATIBILITY.md](PRINTER-COMPATIBILITY.md).

**7 · CI, installer, release.** Build on every PR, tagged releases, published
manifest, web installer on GitHub Pages.

## What must not be lost

The prototype's value is not its structure. It is the set of facts that cost days
to discover, most of which look like arbitrary constants in the code:

- **GPIO43/44, not 6/7.** ([WIRING.md](WIRING.md))
- **The wake-up preamble before every command.** Without it the reader answers
  once and then never again — while still reporting itself ready.
- **Read pages `0x04`–`0x0B` as two 16-byte transactions**, with a 4-byte-per-page
  fallback for a poor link, and a zero-byte count to reject truncated reads.
- **FlashForge acknowledges unknown commands with success.** Always confirm by
  re-reading.
- **FlashForge accepts only its own 24-colour palette** — the public API
  documentation is wrong about this, and a wrong colour is silently reset to
  white while the call returns success.
- **Creality colours are `#0RRGGBB`** — seven hex digits, with a `0` after the `#`.
- **Snapmaker's G-code arguments are space-delimited**, so spaces in vendor or
  material names must be replaced.
- **Bambu Lab's full status report can reach ~50 KB** and needs a large MQTT
  buffer to survive.
- **The FlashForge serial is stored without its `SN` prefix** in the account, and
  the API rejects it that way — the backend has to add it back.
- **The account import already walks all six brands**, Elegoo and Anycubic
  included; only the brand→backend mapping lacks entries for them, so their
  device documents are fetched and discarded. The account plumbing for v1's two
  new brands is done.

Every one of these belongs in a comment that says *why*, next to the code that
depends on it.
